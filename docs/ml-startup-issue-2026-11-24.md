# ML-сервис: медленный запуск — issue для Сергея

Дата замеров: 2026-11-23/24. Контур: seed-база backend (49 773 записи user_anime,
1 006 пользователей, 500 тайтлов), PostgreSQL 14 на localhost, Python 3.10
(venv изолированный, только для диагностики).

Уточнения исходных выводов и проверка исправления на целевом Python 3.12 —
в разделе «Повторная проверка 2026-11-25» ниже. Исходные замеры сохранены.

## Симптом

Сервис рекомендаций «долго запускается»: тянет тяжёлые зависимости и данные,
хотя инференс (`/internal/v1/recommendations/*`) читает только PostgreSQL и
модель для этого не нужна.

## Диагноз

1. **Импорт тренировочного стека на старте инференса.** Цепочка
   `ml/app/main.py` → `app.training.train` → `pandas`; `app.training.train` →
   `app.recsys.als` → `implicit` (+scipy/numpy). Всё это module-level и
   выполняется при каждом старте процесса, хотя `/internal/v1/recommendations/*`
   до них не дотрагивается.
2. **Тяжёлый образ.** `ml/Dockerfile` ставит `requirements.txt` целиком
   (implicit+numpy+scipy+pandas+pyarrow ≈ сотни МБ в образе), а
   `requirements-service.txt` — достаточный для сервинга — не используется.
3. **Пины requirements-service.txt не ставятся на Python 3.10**
   (`pydantic-settings==2.16.1` — только с 3.12). README это знает, но пины
   хрупкие: версии «под текущее окружение», а не диапазоны.
4. **Нет логов длительности этапов старта** — при следующем «медленном
   запуске» нечего будет приложить к issue, как это сделано здесь.

## Задание (приоритет по пунктам)

1. **Ленивые импорты в обучающем пути.** Убрать module-level `import pandas`
   и `from implicit...` из цепочки, которую тянет `app.main`: перенести внутрь
   `run_training` / функций recsys. Критерий: `python -c "from app.main import app"`
   в окружении **без** implicit/pandas/scipy работает, старт до readiness < 0.7 c.
2. **Тонкий serving-образ.** Dockerfile сервиса ставит `requirements-service.txt`
   (+ нужное для чтения БД); обучение — отдельная цель/образ с полным стеком.
   Критерий: размер образа сервиса заметно меньше текущего, `docker run` +
   readiness зелёный без implicit в образе.
3. **Логи длительности старта.** В lifespan: время инициализации engine,
   время до готовности; одна строка в лог вида `startup: ready in 0.42s`.
4. **Пины.** Либо расширить пины requirements-service.txt до диапазонов,
   ставящихся и на 3.10, либо явно зафиксировать «Python ≥ 3.12» в шапке файла.
5. **Опционально**: расписание переобучения и замер длительности train на
   данных, близких к боевым (README: «автоматическое расписание пока не настроено»).

## Повторная проверка 2026-11-25

### Что действительно следует из исходных логов

- `1066541` мкс — суммарный импорт **всего app.main**, а не только обучения.
  Вклад `app.training.train` — `569948` мкс (~0,57 с), в него уже входят pandas
  и implicit. Поэтому утверждение выше «~1,1 с — импорт обучающего стека» завышено.
- Установка пакетов (~36 с), импорт приложения (~1,1 с), ответ readiness (~1,8 с)
  и обучение (~2,8 с) — разные операции. Здесь нет лога Docker build с временем
  шагов, размером контекста или скачиванием базового образа.
- При старте код не читает parquet/модель и не запускает обучение. Данные,
  ноутбуки, артефакты и .venv исключены из ML Docker-контекста.
- Диагностика Python 3.10 использовала другое окружение. Проект и Docker целятся
  в 3.12; это уже явно указано в README и requirements. Оснований ослаблять пины
  или добавлять поддержку 3.10 эти логи не дают.

### Первый этап: исправление импорта

Импорт `run_training` перенесён с уровня модуля `app.main` внутрь функции,
которую вызывает рабочий поток `TrainingJobs`. Это разрывает всю цепочку тяжёлых
импортов для старта HTTP, без переноса импортов по всем алгоритмическим модулям.
API обучения, advisory lock, параметры модели и публикация остались прежними.
Первое обучение теперь включает импорт стека; стоимость не исчезает, а переносится
в операцию, которой этот стек нужен.

На первом этапе полный образ был сохранён: одна замена requirements на service-only
сломала бы POST /train. Дальнейшее разделение образов с сохранением API описано
ниже, в разделе «Второй этап». Исходный образ `anifolder-ml:integration` — 964 MB;
один перенос импорта его размер не уменьшает.

### Собственные замеры

Python 3.12.15, PostgreSQL 16-alpine в отдельном временном контейнере, одинаковые
зависимости и `OPENBLAS_NUM_THREADS=1`. Пять последовательных свежих процессов
до исправления, затем пять после; тесты параллельно не запускались. Исходный код
взят из рабочей ветки до правки. БД для probe содержит таблицу recommendations.

| Медиана от запуска процесса | До | После |
|---|---:|---:|
| HTTP `/health` | 1,0993 с | 0,6345 с |
| HTTP `/health/readiness` | 1,1171 с | 0,6575 с |

Readiness ускорилась примерно на 41%. Это локальные замеры с прогревающимся
файловым кэшем, а не гарантированный SLA <0,7 с на любой машине.
Для замеров запускались отдельные процессы Uvicorn на временных loopback-портах;
время считалось от запуска процесса до первого HTTP 200, затем процесс завершался.
Таймер внутри lifespan не охватил бы предшествующий импорт и не подтвердил бы
соединение с БД. Вспомогательный скрипт использован только для этой проверки
и в проект не включён.

Отдельно проверено внутри существующего образа `anifolder-ml:integration`:
пять процессов с исходным кодом образа, затем пять с текущим `app`, смонтированным
read-only. SHA256 исходного main.py в образе совпал с версией до правки.
Зависимости/образ одинаковые, PostgreSQL тот же; новый образ не собирался.

| Медиана запуска Uvicorn внутри контейнера | До | После |
|---|---:|---:|
| HTTP `/health` | 1,6284 с | 1,0757 с |
| HTTP `/health/readiness` | 1,6415 с | 1,0922 с |

Это улучшение readiness примерно на 33%; время создания самого контейнера
в замер не входит. Отличие от локального venv показывает, почему жёсткий
универсальный порог 0,7 с не следует из исходных данных.

Полный ML pytest: **152 passed**. Новые проверки: в чистом процессе запрещены
импорты обучающего стека, но health/readiness/выдача/статус работают; настоящий
POST /train без подмены trainer обучает ALS и публикует 350 строк в тестовую SQLite.

Сквозной `tests/integration/recommendations_flow.py` прошёл на PostgreSQL16/Python3.12:
миграции0001/0002, seed, регистрация, POST train, 50100 рекомендаций для1002
пользователей (1001 ALS +1 all-time), выдача по Bearer-токену и актуальная фильтрация
списка. Проверены атомарный rollback и advisory lock. Использована отдельная
пустая БД с суффиксом `_ml_integration`; БД разработки не затрагивалась.

### Второй этап: образы, отдельное обучение и логи

Обязательные изменения реализованы:

- Dockerfile: цели `serving` (по умолчанию, только requirements-service.txt)
  и `training` (полные зависимости + libgomp1). Изменения app/logging не сбрасывают
  слои установки зависимостей. В serving проверено отсутствие numpy, scipy,
  pandas, implicit, pyarrow и успешный импорт приложения.
- Compose: `ml` запускается независимо; `ml-training` включается явно профилем
  `training`. Только обучающий контейнер монтирует том артефактов. ML-порты наружу
  не публикуются. Итоговая конфигурация Compose проверена.
- Старые URL POST train и GET статуса на `ml` сохранены через `ML_TRAINING_URL`.
  Команды передаются обучающему сервису; 202/409/статус сохраняются. При его
  недоступности — 503 TRAINING_UNAVAILABLE, без автоматического повтора POST.
  GET рекомендаций и readiness продолжают работать. Без ML_TRAINING_URL
  локальный режим с полными зависимостями обучает в том же процессе.
- `logging.json` включён в Docker CMD: логируются длительности импорта,
  создания engine, lifespan и первая успешная проверка БД. Последний таймер
  явно включает задержку до probe; создание engine не названо готовностью БД.
- Python >=3.12 уже явно указан в requirements/README. Поддержка3.10 и ослабление
  пинов не добавлялись. Опциональные расписание и инкрементальность не реализованы.

Размеры из `docker image inspect` (десятичные MB, не размер скачивания):

| Образ | Байты | MB |
|---|---:|---:|
| Исходный полный | 963759604 | 963,8 |
| Новый serving | 311674291 | 311,7 |
| Новый training | 959342558 | 959,3 |

Serving меньше исходного примерно на 68%. Полный стек по-прежнему нужен для
обучения, но обычная сборка `ml` его больше не устанавливает. Контекст первой
новой сборки — 210,19 kB; установка service-зависимостей — 30,3 с. Отдельная
training-сборка добавила 15,3 с apt и 41,8 с pip. Это конкретные сетевые замеры,
не гарантированное время на другой машине; базовые слои между целями общие.

Пять запусков на том же PostgreSQL16, без параллельных тестов, внутри контейнеров:

| Медиана readiness | Секунды |
|---|---:|
| Исходный полный образ | 1,8528 |
| Новый serving (Python3.12.16) | 1,0852 |

Новый образ собирался заново, поэтому это сравнение итоговых образов, а не
изоляция эффекта одной строки кода при идентичных транзитивных зависимостях.
**Критерий readiness <0,7 с в Docker на этом стенде не достигнут.** Его нельзя
считать выполненным по времени одного lifespan. Для приёмки требуется согласовать
целевой стенд и условия замера либо отдельно продолжать оптимизацию запуска.

Пример настоящего лога serving:

```text
ML startup: imports=0.683s engine=0.147s lifespan=0.160s training=remote; database readiness not checked yet
```

Проверки второго этапа после саморевью: **165 ML-тестов прошли**. Обрыв HTTP-ответа
обучающего сервиса обрабатывается как503, без повторного POST; проверены и запуск,
и получение статуса (два регрессионных теста сначала воспроизвели ошибку).
Сквозной сценарий отдельно прошёл
через настоящие serving/training-образы и в прежнем локальном режиме: по50100
строк для1002 пользователей, авторизация, фильтрация списка, rollback, advisory lock.
Для Docker-пары использован `--ml-url` существующего интеграционного теста.
После остановки training контейнер serving сохранил HTTP200 для readiness/выдачи,
POST train и GET статуса вернули503 с ожидаемым кодом. Вспомогательный измеритель
в проект не возвращался. Тестовые контейнеры и сеть после проверки удалены.

### Третий этап: прямой psycopg в выдаче

После профилирования убран SQLAlchemy из HTTP-пути. Он перенесён в полный
requirements.txt и `app/training/db.py`, импортируется только при обучении.
Два SELECT выдачи выполняются через psycopg с параметрами, psycopg-pool==3.3.3,
autocommit, проверкой соединения перед выдачей из пула и ограничением ожидания.
Пул начинает с0 соединений, максимум15 (как прежние5+10 overflow SQLAlchemy),
timeout5с, очередь до40 запросов. Readiness по-прежнему выполняет настоящий SQL;
при ошибках БД/таймауте/закрытом пуле —503. Пул закрывается при shutdown.
У локального обучения отдельный SQLAlchemy engine, создаваемый и освобождаемый
внутри задания. Формат API, ранжирование и параметры модели не менялись.

Сравнение по5 последовательных процессов каждой версии на одной PostgreSQL16,
OPENBLAS_NUM_THREADS=1, без параллельных тестов/сборок. Включён одинаковый logging.json.
Для локального сравнения использовано одно окружение Python3.12.15; исходный app
сохранён до рефакторинга. Для Docker — serving-образы до/после, Python3.12.16.

| Медиана до readiness | С SQLAlchemy | Прямой psycopg |
|---|---:|---:|
| Локальный Python | 0,7190 с | 0,5799 с |
| Docker | 1,1297 с | 0,9344 с |

Дополнительное ускорение примерно19% локально и17% в Docker. Новый serving-образ
277886213 байт (~278MB) вместо311674291 (~312MB). SQLAlchemy, numpy, pandas, scipy,
implicit и pyarrow в serving не требуются. Численный Docker-критерий <0,7с всё ещё
не достигнут; результаты сравниваются внутри этого прогона, поскольку загрузка
машины/файловый кэш меняют абсолютные значения между сессиями.

После рефакторинга и выравнивания поддержки PostgreSQL URL полный ML pytest:
**172 passed**. Чистый subprocess запрещает
также SQLAlchemy и всё равно выполняет health/readiness/выдачу. SQLite-тестовый
адаптер исполняет настоящие запросы RecommendationStore, заменяя только DB-API
соединение и синтаксис placeholders. URL-тесты проверяют сохранность пароля и
query-параметров при переходе от postgresql+asyncpg к libpq URL. Таймаут/закрытый
пул возвращают503 без внутренних деталей.

Сквозной тест расширен проверкой настоящего пула: его PostgreSQL-соединение
принудительно закрывается, следующий запрос восстанавливает рабочее соединение,
возвращает прежние рекомендации, затем пул явно закрывается.

Проверка прошла и в локальном режиме, и через новые Docker-образы
`serving-psycopg-check`/`training-psycopg-check`: по50100 рекомендаций для1002
пользователей, auth/current-list/rollback/advisory lock/pool reconnect.
В новом serving отдельно подтверждены успешный импорт приложения и физическое
отсутствие SQLAlchemy и пяти обучающих библиотек. Training-образ —959833932 байт;
полный стек обучения сохранён. Пример лога нового serving:

```text
ML startup: imports=0.665s pool=0.003s lifespan=0.022s training=remote; database readiness not checked yet
```

Рефакторинг оставлен: сокращение времени и размера подтверждено, контракт и
работа обучения сохранены. Вспомогательный измеритель оставался только в /tmp,
в репозиторий не добавлялся.

Тестовые контейнеры `anifolder-psycopg-serving`, `anifolder-psycopg-training`,
`anifolder-psycopg-pg` и сеть удалены после проверки; БД разработки не затрагивалась.
